## 0. 为什么需要这张表（实测根因）

竞彩↔模型是**按中文名 join** 的，模型产出的中文名必须与竞彩官方名**逐字相等**：

| 位置 | join 键 | 证据 |
|---|---|---|
| `/api/v1/ticket/sfc`（传统足彩 14 场/任九） | `fact.jc_issue_match.home_cn` ↔ 预测 entry 的 `home`/`away` | `web/routers/ticket.py:110` |
| `/api/jc/gap`（错位榜）、`/api/jc/daily-image`（每日一图） | 竞彩 `home_cn`/`away_cn` ↔ 预测 `home`/`away` | `web/services/team_match.py:328` |

### 0.1 为什么不并进 `team_translations.json`

那个文件是 **LLM 翻译缓存**，`core/i18n.py::save_translations()` 每次预热都**整文件重写**
（`i18n.py:64-72`）⇒ 人工核对表混进去会被下一次 LLM 预热冲掉。必须独立成文件。

### 0.2 优先级链（改后）

```
to_cn(name):
  ① team_cn_official.json  竞彩官方名（人工核对，最高优先级）
  ② COUNTRY_CN             国名 + 兼容的旧俱乐部叫法
  ③ team_translations.json LLM 翻译缓存
  ④ 原样返回英文
```

## 4. 核验方法与结果

1. 从 Oracle `league` 库只读导出 `fact.jc_match` 的 396 个去重竞彩队名（`home_cn` ∪ `away_cn`）。
2. 逐条比对本表的**取值**与该 396 集合 ⇒ 结果见 §1 最后一列。
3. 比对本表的**键**与 `COUNTRY_CN` / `team_translations.json` ⇒ 冲突项见 §2。
4. **交叉检查**：同一中文名不得对应两支不同俱乐部 —— 全部通过
   （`AS Monaco`/`Monaco` → 摩纳哥、`AS Roma`/`Roma` → 罗马、`Internazionale`/`Inter Milan` → 国际米兰 等，
   都是**同一支队的不同源拼写**，不是两支队）。

### 4.1 核验过程抓到的自身错误（留档）

初稿把 Celta Vigo 写成「塞尔塔」（沿用 `COUNTRY_CN` 的通用叫法）。
与 396 队名逐条比对时**没有**「塞尔塔」，只有「**维戈塞尔塔**」⇒ 判定初稿错、
`COUNTRY_CN` 错，改为「维戈塞尔塔」。
⇒ **教训**：通用叫法在这张表里一律不可信，必须以竞彩 396 队名为准。
