# 国内采集机实施文档（Prompt 交付版，2026-09-15）

> **契约版本 v1.1（2026-09-15 冻结）**：§5 已按国内机回传的 `probe_pack.tar.gz`（13 次探针全 200）逐字段改写为官方真实键名。取证与差异清单见 `探针核对报告-v1.1-20260915.md`。字段契约以本文件 §5 为准，改 §5 必须升版本号并回写 `collector.status.json:contract_version`。

> 交给国内机器上的 AI 执行。定位：一个只做"取官方 JSON → 落 JSONL 文件 → 推送到远端"的独立小工具。
> **它不连数据库、不解析 HTML、不装重型依赖，也不做任何字段改名/清洗/判断。** 字段契约以本文件 §5 为准，不得自创字段名；
> 探针阶段已完成，接下来是**正式采集模式**（§6 节奏 + §5.8 十分钟快照）。

## 1. 背景与目标
league-predict 系统需要中国体育彩票官方口径数据（竞彩盘口/让球线/单关资格/固定奖金、传统足彩奖期与奖级、篮彩盘口、数字彩开奖）。官网接口域名 `webapi.sporttery.cn` 海外 IP 实测被挡，需在**国内机器**部署采集器定时抓取，产出 JSONL 文件推送到远端服务器（oracle），由远端负责入库 PostgreSQL。

## 2. 运行环境要求（最小集）
- Python ≥ 3.9，仅允许 stdlib（urllib/json/hashlib/pathlib）+ 可选 requests；**禁止** selenium/bs4/scrapy/pandas。
- 系统具备 `rsync` 或 `scp` + `ssh`（出站连通 oracle:22 即可，国内访问 AWS 东京一般可达；不通则见 §6 兜底）。
- 时钟与 **Asia/Shanghai 时区**必须正确（接口业务按北京时间截止；所有输出时间戳一律转 UTC ISO8601 带 Z）。
- 单进程 cron 运行；不做并发窗口。

## 3. 第一步永远是探针模式（probe），不是抓数
所有候选接口（§4）标注"待验证"——我（海外侧）无法直连确认响应结构。**实施顺序强制为：先 probe → 把探针包回传 → 等契约冻结 → 再写解析。**

```bash
python3 collector.py --probe            # 逐个 GET §4 端点，UA=浏览器标准值，Referer=https://static.sporttery.cn/
                                      # 每端点记录：HTTP状态、content-type、响应前 800 字符（截断）
                                      # 产出 probe_pack.tar.gz → 按 §6 通道推送
```
- 若某端点返回反爬 HTML（非 JSON）：换 UA/Referer 重试 2 次，仍失败则标记 `BLOCKED` 并继续下一端点，**绝不转 HTML 解析**。
- 探针包回传后由海外侧核对字段并冻结 §5 契约（版本号 +1），解析代码只允许消费冻结后的字段。

## 5. 输出契约 **v1.1**（2026-09-15 依探针包冻结；JSONL，每 topic 每批一个文件）

> **契约版本：v1.1**（v1 为探针前的骨架）。改任何契约内容必须把这里的版本号 +1，并在 `collector.status.json` 里回写 `contract_version`——远端按版本号判断解析器分支，不会静默兼容。
> 依据：`探针核对报告-v1.1-20260915.md`（13 次探针全 HTTP 200；下面每个字段名都取自**真实响应**，不是文档推测）。
> **总原则：采集机是搬运工，不是分析师。** payload 里放**官方键原样**（键名、值、类型一律不动：官方给字符串就是字符串，给 int 就是 int，空串就是空串）。改名、换算时区、清洗千分位、判奖——全在远端 `scripts/store/parse_collector.py`。这样官方改字段时只有远端需要动代码。

### 5.0 通用行外壳（七个 topic 完全一致）
```json
{"kind":"line","topic":"jczq_offer","snap_ts":"2026-09-15T13:00:00Z","endpoint":"https://webapi.sporttery.cn/…","http_status":200,"collector_host":"cn-collector","payload":{…},"src_hash":"…"}
```
- `snap_ts`：**UTC、必须带 `Z`**，＝本次请求发出时刻（同一批内所有行同一个值）。官方自带的更新时间（如 `oddsList[].updateDate/updateTime`、`value.lastUpdateTime`）留在 payload 里，**不许顶替 snap_ts**。
- `kind="error"`：当 `errorCode != "0"` 或 `success != true` 时**必须产这一行**（不是跳过！），payload 原样放 `{errorCode, errorMessage, emptyFlag, dataFrom}`（失败响应实测**没有 `value` 键**。远端要靠这条区分"该期真没比赛"和"接口挂了/参数错了"，两者在 HTTP 层都是 200）。
- `src_hash` = `sha256(json.dumps(payload, ensure_ascii=False, sort_keys=True, separators=(",", ":")).encode("utf-8"))` 的十六进制小写。**必须用这个官方序列化式**，不许手拼字符串（远端拿它做幂等键，算错一次就会重复入库）。
- 每行的**身份键**（远端按"身份 + snap_ts"重建盘口时序并幂等回放）。采集机不必实现这层逻辑，只需保证这些键存在于 payload：offer/result 类 = `matchId`；`jc_issue`/`jc_issue_result`/`lottery_draw` = `(lotteryGameNum, lotteryDrawNum)`。
- 文件名/目录/编码/`.done`/`.empty`/追加不覆盖：沿用 §6、§7 原文（UTF-8、一行一对象）。

### 5.1 `jczq_offer` —— 一行 = **一场 × 一个玩法**
树：`value.matchInfoList[].subMatchList[]`（一场 46 键），对 `had | hhad | crs | ttg | hafu` **五块各产一行**：
```json
{"matchId":2041483,"matchNum":2004,"matchNumStr":"周二004","matchNumDate":"260915",
 "businessDate":"2026-09-15","matchDate":"2026-09-15","matchTime":"20:15:00",
 "leagueId":24,"leagueAllName":"…","leagueAbbName":"…",
 "homeTeamId":2117,"awayTeamId":1667,"homeTeamAllName":"…","awayTeamAllName":"…",
 "homeTeamAbbName":"…","awayTeamAbbName":"…","homeRank":"…","awayRank":"…",
 "matchStatus":"Selling","sellStatus":1,"bettingSingle":0,"bettingAllUp":…,
 "poolCode":"HAD","block":"had","options":{…整块原样…},
 "oddsHistory":[…该场 oddsList[] 原样…]}
```
- `block` 填五个玩法键名之一，`options` ＝该块**整块原样**（含 `h/d/a`、`goalLine`、`goalLineValue`、各 `*f` 旗标、`updateDate/updateTime`）。`poolCode` 用对应官方码（实测 `HAD/HHAD/CRS/TTG/HAFU`）。
- **不许拆比分**：`crs` 块含 31 个选项键（实测 `s00s00`…`s05s02` + `s1sh/s1sd/s1sa`，每个另带 `…f` 旗标），远端派生层与它**逐键一一对应**，拆行只会把 5341 场炸成 16 万行。
- `oddsHistory` 原样搬，**不要按 poolCode 去重或排序**。⚠️ 实测 `oddsList[].matchId/matchNum` 恒为 `0`（官方不回填）⇒ 千万别拿它当关联键，用外层 `matchId`。
- ⚠️ `hhad` 才有的 `goalLine="-1"` / `goalLineValue="-1.00"` 是**让球线**（本次探针最大收获，远端 `hhad` 玩法靠它解锁）。
- **不落**（v1.1 未纳入，要加先升版本号）：`value.allUpList`（过关组合公式表）、`value.poolList`、`vtoolsConfig`、`leagueList`、`matchDateList`。

### 5.2 `jczq_result` —— 一行 = 一场
请求 `getUniformMatchResultV1.qry?matchBeginDate=&matchEndDate=`；payload = `value.matchResult[]` 整条原样（25 键）。
- 关键字段（实测语义，远端负责解析，采集机不要改名）：`sectionsNo1`＝**半场比分**、`sectionsNo999`＝**全场比分**、`h/d/a`＝胜平负 SP、`goalLine`＝让球线（**实测含正号 `"+4"`**）、`winFlag ∈ {"H","A",""}`、`matchResultStatus`（`"2"` 完场 / `"0"` 取消）、`matchNumStr`（"周一014"）、`homeTeamId/awayTeamId`、`allHomeTeam/allAwayTeam`（全名）与 `homeTeam/awayTeam`（简称）。
- ⚠️ **取消场次实测**：`sectionsNo999="取消"`（中文！）、`sectionsNo1=""`、`h/d/a=""`。⇒ **照原样产这行**，不许置 null、不许改 0、不许跳过。
- ⚠️ 实测 14 场里只有 9 场 `h` 非空（亚运女足等非竞彩开盘场次）⇒ 空 SP 是常态不是异常。
- 增量：按北京当日抓（`matchBeginDate=matchEndDate=北京日期`）；**历史回填窗口等远端下发，不要自己往前扫**。

### 5.3 `jc_issue` —— 一行 = 一个玩法的一期期头
`getFootBallConcernV1.qry?param=<gameNum>,0`，**玩法号已由探针定死**：
| `param` | `lotteryGameName` | 实测场数 |
|---|---|---|
| `90` | 胜负游戏（14 场） | 14 |
| `900129` | **任选9场** | **14**（14 场候选里选 9） |
| `98` | **6场半全场** | 6 |
| `94` | 4场进球 | 4 |
```json
{"lotteryGameNum":"90","lotteryGameName":"胜负游戏","lotteryDrawNum":"26126",
 "lotterySaleBeginTime":"2026-09-13 20:00","lotterySaleEndTime":"2026-09-15 19:45","lotteryDrawTime":"2026-09-16 14:00",
 "drawNumList":["26126","26127",…],"matchList":[…整条原样（9 键）…]}
```
- ⚠️ **期号跨玩法会重号**（`90` 与 `900129` 同期都是 `26126`）⇒ `lotteryGameNum` 必须在 payload 里，不能只存期号。
- ⚠️ 场数**不许按常识断言**（任九给 14 场就是反例）：数组多长就写多长。
- ⚠️ `masterTeamName` 含**全角空格**（实测 `"国  安"`、`"浦  项"`）⇒ 原样保留，别 trim 内部空格（远端用 `*AllName` 全名与 `gmMatchId` 对齐；`gmMatchId` 与竞彩 `matchId` **同源**，是三条链路串起来的钥匙）。
- `startTime` 实测**只有日期**没有时刻 ⇒ 原样存，远端再用 `matchId` 去竞彩侧补时刻。
- `value.drawNumList`（可售期号数组）必须随每行带上（远端据此发现漏抓的期）。

### 5.4 `jc_issue_result` —— 一行 = 一个玩法的一期开奖
`getFootBallDrawInfoV2.qry?isVerify=1&param=94,0;90,0;98,0`（一次返回 `sfc/jqc/bqc` 三棵树）。每棵各产一行，payload = `*Detail` **整条原样**（31 键）+ 额外加一个 `"gameKey":"sfc|jqc|bqc"`。
- 任九（`900129`）**不单独抓**：它作为 `*Rj` 孪生字段（`totalSaleAmountRj`、`poolBalanceAfterdrawRj`…）和 `prizeLevelList` 里"任选9场"那一行混在 sfc 期内 ⇒ 整条原样搬即可，别做拆分。
- ⚠️ 官方拼写 **`lotterySaleEndtime`**（少一个 a）——照抄，别"纠正"成 `lotterySaleEndTime`。
- ⚠️ `matchList[].result` 三玩法形态**不同**（实测）：`sfc` `"3"`（3 胜/1 平/0 负）；`jqc` `"3＋,1"`（主档,客档，**全角加号**）；`bqc` `"3,3"`（半场,全场）⇒ 原样存，判奖口径远端定。半场另有 `czHalfScore="2:1"`、全场 `czScore="5:1"`。
- ⚠️ `prizeLevelList` **长度不固定**（实测 sfc 3 条、jqc 1 条），且 `stakeAmount` 带千分位逗号（`"12,387"`）、浮动奖未定时为 `""`（实测一等奖三项皆空）⇒ 两个字段都原样搬，别自己转数字。

### 5.5 `jclq_offer` —— **v1.1 不冻结**（探针窗口内篮彩确实无开售，不是采集失败）
实测 `uniform/basketball/getMatchCalculatorV1.qry?channel=c` 返回 `errorCode="0"` 但 `value` 只有 `vtoolsConfig`（NBA/CBA 休赛期）。
⇒ 每天仍照抓一次；**首次抓到非空时**：按 §5.1 的结构产行，同时在 `collector.status.json` 写 `"jclq_offer":"unverified-shape"` 并**单独回传一份探针包**给远端，远端出 v1.2 正式冻结该段。不许凭推测改字段名。

### 5.6 `jclq_result` —— 一行 = 一场
`uniform/basketball/getUniformMatchResultV2.qry`（⚠️ 篮球是 **V2**，足球是 V1）；payload = `value.matchResult[]` 整条原样（22 键）。
- ⚠️ 三个实测陷阱：① `finalScore` 用**连字符**（`"61-105"`，足球侧是冒号 `"2:1"`）；② `status` 是 **int** `2`（足球同义字段 `matchResultStatus` 是 str `"2"`）；③ 四个玩法块结构同构 `{combination, combinationDesc, goalLine, winOdds, single, resultStatus}` 但**语义各异**：`mnl`＝胜负（实测 `"主胜"`）、`hdc`＝让分胜负（`goalLine "-25.5"`）、`hilo`＝大小分（`goalLine "171.5"`）、`wnm`＝胜方分差段（实测 `combination "+4"` / `combinationDesc "主胜16-20"`）。
- ⚠️ 块里 `resultStatus` 实测可能是**中文 `"未开售"`** 或 `""` ⇒ 原样存，别映射成枚举；四块不许合并或改名（远端定名）。

### 5.7 `lottery_draw` —— 一行 = 一个彩种的一期
`getHistoryPageListV1.qry?gameNo=<号>&provinceId=0&isVerify=1&termLimits=30`；号与彩种实测对应：`85` 超级大乐透 / `35` 排列3 / `350133` 排列5 / `04` 7星彩。payload = `value.list[]` 整条原样（43 键）。
- ⚠️ `lotteryDrawResult` 是**空格分隔号码串**：大乐透 `"10 14 30 33 34 09 12"`（前区 5 ＋ 后区 2）、排列3 `"0 5 1"`、排列5 `"0 5 1 9 8"`、7星彩 `"5 1 9 5 8 5 11"`（6 位 ＋ 特别号）⇒ **别拆、别排序、别去重**，原样一条。
- ⚠️ `prizeLevelList` 长度随彩种变（实测 1/3/6/9），金额字段同样带千分位 + 有 `*Format` 干净版 ⇒ 两者都原样。
- `termList / termResultList / matchList / prizeLevelListRj / vtoolsConfig` 实测**恒为空数组或空对象**（是跟足球共用的接口壳）⇒ 随它原样，远端白名单外不读。
- 数字彩**只做开奖对照，远端不进任何模型**（红线，见 §9）；`value.lastPoolDraw` 只在需要奖池时留最新一期，不必每行重复。

### 5.8 定时快照的新增硬要求（为了真实收盘盘口）
`jczq_offer` 与 `jclq_offer` 除 §6 的四个固定时点外，**每 10 分钟各加一次快照**（同一 `matchId` 的多条 `snap_ts` 就是盘口时序；封盘前最后一条即远端认定的"收盘价"，是 CLV/EV 的唯一可信来源）。这决定远端能不能算出真实价值，请优先保证不断档；单次请求失败按 §7 退避重试并产 `kind="error"` 行。

## 6. 推送通道与节奏
```
cron（北京时间）：
  09:30 / 15:30 / 21:30 / 次日01:30  → jczq_offer, jclq_offer（开售场次+SP 快照，全量）
  23:05 → jczq_result, jclq_result（当日开奖）
  20:10 → jc_issue；22:40 → jc_issue_result（有开奖的奖期才产文件）
  23:30 → lottery_draw（当日有开奖的 game）
推送：rsync -e "ssh -p22 -i ~/.ssh/league_id" --partial --backup \
        ./out/ league@<ORACLE_IP>:/srv/league-staging/incoming/<collector_host>/
完成后 touch 同名 `.done` 文件（远端 ingest 只认 .done，且要求文件名含 UTC 时间戳）。
兜底：若 ssh 不通 → 每日打包 7z 放指定网盘/邮件，人工转进 incoming/；采集器本地保留 30 天滚动副本可重推。
```

## 7. 健壮性与红线
- QPS ≤ 1，重试 3 次指数退避（5/15/45s）；连续失败写 `collector.status.json`（远端做新鲜度监控，不告警骚扰）。
- 只 GET 公开 JSON 接口；不登录、不存 cookie/token、不下载页面资源。
- 输出文件追加写禁止覆盖历史批；单批行数 = 0 也要产 `.empty` 标记（区分"没抓到"和"接口挂了"）。
- 时间戳三件套：`snap_ts`(接口口径) / `fetched_at`(本地) / 文件名 UTC——远端 ingest 以 snap_ts 去重回放。

## 8. 验收清单（国内机 AI 交付自证）
1. probe_pack 回传，7 个 topic 各自 HTTP 状态与样例行已确认；
2. 契约冻结后：连续 3 天 cron，`incoming/` 下 7 topic 的 `.jsonl+.done` 齐全，行数>0（非比赛空档日允许 `.empty`）；
3. 抽 10 行与官网页面肉眼核对 SP/让球线/单关标记一字不差；
4. 断网 1 小时后恢复：自动补推，无重复行语义（src_hash 生效）。

## 9. 不在范围（明确禁止）
爬虫/HTML 解析、北单、直接连 PG、装重型依赖、对接口做逆向签名、任何写死"我以为"的字段名。
