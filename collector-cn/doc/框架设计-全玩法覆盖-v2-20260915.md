# league-predict 全玩法覆盖 · 代码框架设计 v2（2026-09-15）

> 前提决策已锁定：范围=竞彩足球(6联赛)6玩法 + 传统足彩4玩法 + 篮彩(NBA/CBA)3玩法 + 数字彩4种(管理/组合/EV定位)；无国内出口给海外服务（官方数据走国内采集机文件推送）；免费档 API 先行（开盘+临场两快照，只抓竞彩开售场）；串关=EV报告无票单UI；北单排除；部署目标 oracle Nginx（FastAPI Cloud 退役）。

## 0. 硬性红线（写进每张工单）
- 新代码**函数化、功能化**：纯函数优先，I/O 只在 store/ingest 层；
- **单文件 ≤100 行、单函数 AST ≤50 行**（沿用 M7 战役基线）；预估超 100 行的模块必须先拆文件或提交例外说明进工单；
- 唯一新增第三方依赖：`psycopg[binary]`（仅 store 层；模型 core 保持 stdlib 零依赖不变）；
- 不改现有 `scripts/core` 模型内核，新链路全部以"下游派生"方式挂接。

## 1. 分层架构（单向数据流）
```
L0 采集        L1 入库        L2 内核(已有)      L3 派生            L4 决策支持     L5 展示
ingest/  →  store/(PG UPSERT)  →  core/模型    →  derive/ + market/  →  combo/       →  nginx 静态/报告
国内机CSV →  ingest_pull        ELO/DC/MC/ML   矩阵→各玩法概率/CLV   EV/串关/Kelly   AI摘要(ai_ref标记)
```
现有三处取数重叠（predict.py 直调、web job、cron）统一收敛到 `pipeline/`；FastAPI Cloud 退役后 web/ 仅保留只读 JSON 导出（或整体改造，部署迁移是独立工单，不在本设计内展开）。

## 6. 多源标注优先级（2026-09-15 实测确立，回测/训练取数必须照此）

**背景**：`fact.fixture_result` 用 `PK(fixture_id, source)` 让 AF/FD 两源并存、互不覆盖；但**下游取数必须有唯一确定的标注口径**，
否则同一场比赛会有两个"真值"进回测。口径不是拍脑袋定的，是用逐事件原始数据当场裁出来的：

| 项 | 规则 | 根据 |
|---|---|---|
| fixture 身份 | **AF `fixture.id` 为权威 id**；FD id 只进 `fact.fixture.source_ids` | 同秒多场是常态 ⇒ 对齐靠 (league_key, 开球时刻) 取候选 + 队名 token 子集/同义表定"配对唯一"（`store/align.py`，对齐率 99.3%） |
| 比分标注 | **一律取 `source='api_football'` 行**；FD 行**只做交叉核对**，永不参与训练/回测 label | 3481 场双源里 2 场分歧，两场都用 AF `/fixtures/events` 逐事件裁定 **AF 正确**（见下） |
| 半场标注 | **只信 AF 的 `score.halftime`**（5341 场 0 缺失）；FD 的 `halfTime` 已知会**把全场抄进半场** | 分歧样本 1223728：进球 59'/68'/89' ⇒ HT 必为 0:0，AF=0:0 ✅、FD=3:0 ❌ |
| 分歧处理 | 分歧场**不许静默丢弃**，必须能列出来（`fact.v_result_conflict`）；分歧率进体检报告 | 当前 2/3481 = **0.06%** |
| 未知联赛/队 | 计 `skipped` 并留痕 `ops.ingest_log`，**不许猜 id** | 同 §0 红线 |

两次分歧的原始证据（花 2 次 AF 请求，其中 1 次命中 raw 缓存 ⇒ 实际净耗 1 格配额）：
```
1223728  seriea 2024  佛罗伦萨 vs Inter        AF ht 0:0 ft 3:0 | FD ht 3:0 ft 3:0
         events: 59' Ranieri(FIO) 68' Kean(FIO) 89' Kean(FIO)  ⇒ 半场 0:0 ⇒ AF 对，FD 抄送
1224099  bundesliga 2024  柏林联合 vs VfL Bochum  AF ht 1:1 ft 1:1 | FD ht NULL ft 0:2
         events: 23' Sissoko(BOC) 33' Hollerbach(FEU)          ⇒ 全场 1:1 ⇒ AF 对，FD 记错
```

半场数据体检（纯 SQL，零配额）：`ht_* > ft_*` 的不可能情形 **0 行**；
`ht == ft 且非 0:0` 占比 AF 13.7% / FD 13.0%，与"下半场双方均无进球"的泊松先验（≈13.5%）吻合 ⇒ **不是抄送嫌疑，是正常分布**。
### 6.1 竞彩/足彩官方数据可算性（2026-09-15 探针核对后确定，取证见 `探针核对报告-v1.1-20260915.md`）

| 玩法 | 官方盘口来源（webapi.sporttery.cn） | 判奖来源 | 现在的结论 |
|---|---|---|---|
| `had` 胜平负 | `jczq_offer` → `subMatchList[].had` {h,d,a} | `jczq_result.h/d/a` + `winFlag` | 可算，SP 原值直用 |
| `hhad` 让球胜平负 | 同场 `hhad` 块，**含 `goalLine="-1"`/`goalLineValue`** | `sectionsNo999` + `goalLine` | **当场解锁**（P0-MODEL1 曾因"缺官方让球线"只写 had/crs/ttg/jqc） |
| `crs` 比分 | 同场 `crs` 块 **31 选项** | `sectionsNo999` | 与 `derive/scores31.py` **逐键相等**，零口径偏差 |
| `ttg` 总进球 | 同场 `ttg` 块 `s0…s7`（s7＝"7+"） | `sectionsNo999` | 与 8 桶 1:1 |
| `haf` 半全场 | 同场 `hafu` 块 9 组合 | **`jc_issue` param=98「6场半全场」** + 官方 `sectionsNo1`/`czHalfScore` | 数据前提齐了（原以为"半场比分不稳"）；派生层尚未注册 |
| `jqc` 4场进球 | 无盘口（传统足彩按奖级派奖） | `jc_issue_result.jqcDetail.result="3＋,1"`（**每场 主档,客档**，"3＋"含全角加号） | 需两侧编码 + 与官方 4 档（0/1/2/**3+**）归并：`derive/goals4` 现在是 5 档 '0'..'4' ⇒ 在 model 侧把 '3'+'4' 并成 '3+' |
| 篮彩 `hwtx/rfssf/dxf` | **`jclq_offer` 未探到**（窗口内无开售） | `jclq_result` 的 `mnl`(胜负)/`hdc`(让分胜负 −25.5)/`hilo`(大小分 171.5)/`wnm`(胜方分差段) | 赛果侧齐；盘口侧 10 月复探；`finalScore="61-105"` 是**连字符** |
| 数字彩 4 种 | — | `lottery_draw` `gameNo=85/35/350133/04`，`lotteryDrawResult` 空格分隔号码串 | **只做开奖对照，不进任何模型**（红线不变） |

**多源优先级（补充）**：足球场次身份仍以 **AF `fixture.id` 为权威**；竞彩侧另有官方 `matchId`/`homeTeamId`/`awayTeamId` 与 `gmMatchId`（＝竞彩 `matchId`，传统足彩与竞彩同场可直连）
⇒ `ref.team.aliases` 将增加第三个源键 **`sporttery`**，国内机数据一律**按官方 team id 认队**（今天刚被"按译文名认队"坑过，绝不在新链路上重犯）。
