## 3. 通用信封（七个 topic 完全一致，冻结）
```json
{"dataFrom":"","emptyFlag":false,"errorCode":"0","errorMessage":"处理成功","success":true,"value":{…}}
```
- **成功判据 = `errorCode == "0"`（字符串！）且 `success === true`**；失败样例实测：`{"errorCode":"P0001","errorMessage":"参数不合法","success":false,"dataFrom":null}` 且**没有 `value` 键**。
- ⚠️ 三个易踩的空态必须可区分，故 §5 要求错误也要出行：① `errorCode=P0001`（参数/期号错）② `errorCode="0"` 但数组为空（**该期/该日确实无场次**，如今天篮彩）③ 网络层失败（无响应体）。
- 时间字段一律**北京时间裸串** `"2026-09-15 19:45"`（无时区后缀），日期 `"2026-09-15"`，时刻 `"20:15:00"` ⇒ 契约里 `kickoff_bj` 保持原值，**换算 UTC 由远端做**。

## 5. 与 v1 骨架的差异（就是这次冻结要改的东西）
| v1 骨架写法 | 探针实测 | v1.1 处置 |
|---|---|---|
| 7 topic 的 `.line` 语义字段名（自造英文名） | 官方键名是 camelCase 中文语境名 | **改为"官方键原样 + 白名单"**：行内放 `{"kind":"line","payload":{…官方原子集…}}`，不再要求采集机改名映射 |
| `crs` "允许一行=一个格" | 官方一块 31 键一次给全 | **一行 = 一个（场次 × 玩法）**，`options` 整块存；否则 5341×31 行没必要 |
| `play_type` 枚举含"过关组合类" | 过关公式在 `value.allUpList`（另一棵树） | v1.1 **不落过关表**（列为待定，见 §6） |
| `jc_issue` 一个 `game:"14c\|rq\|bqc\|jqc"` | 官方号是 `90/900129/98/94`，且**期号跨玩法会重号** | 冻结为 `game_num` 原值 + `issue_no`，**两列一起作幂等键** |
| `jclq_offer` 与足球同构 | 窗口内无开售，未验证 | 该段**不冻结**，标"待复探"，复探件同契约回传 |
| 队名"官方中文原值" | 官方同时给 全名/简称/英文缩写/**带全角空格**四种 | 一律存 `*AllName`（全名）进 `home_cn/away_cn`，其余原样留在 payload；**远端按官方 team id 认队**（今天远端自己被"按译文名认队"坑过一次，见 P0-TEAMKEY1） |
| 无"失败也要出行"要求 | 实测 `P0001` 与"空数组"都返回 HTTP 200 | **新增硬要求**：`errorCode≠"0"` 必须出一条 `kind="error"` 行（否则远端无法区分"没比赛"和"没抓到"） |
| `snap_ts` 只在 offer 里要求 | 盘口是随时变的（`oddsList` 自带 `updateDate/updateTime`） | **所有 topic 每行都必填 `snap_ts`**（UTC，`…Z`），另存官方 `updateDate/updateTime` 原值 |
